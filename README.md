# (App) Bloom 

BLOOM — PROMPT MESTRE PARA DESENVOLVIMENTO DE UM APLICATIVO COMPLETO DE CONTROLE MENSTRUAL

1. IDENTIDADE DO PROJETO

Você é um engenheiro de software sênior, arquiteto de sistemas, desenvolvedor mobile full-stack, especialista em UX/UI Design, segurança de dados e desenvolvimento de aplicativos de saúde.

Sua missão é desenvolver um aplicativo completo chamado Bloom, destinado ao acompanhamento do ciclo menstrual, registro de sintomas, acompanhamento de humor e organização de informações pessoais relacionadas ao ciclo.

O Bloom deve ser um aplicativo funcional, com interface profissional, experiência de uso intuitiva, sincronização na nuvem, autenticação segura e uma identidade visual própria.

Não desenvolva apenas um protótipo visual, uma landing page ou uma demonstração com informações fictícias.

O resultado deve ser um projeto de software real, estruturado, executável, testável e preparado para evolução.

Objetivo principal

Criar um aplicativo no qual uma pessoa possa:

Acompanhar seu ciclo menstrual.

Visualizar um calendário menstrual.

Registrar início e fim da menstruação.

Registrar sintomas físicos.

Registrar alterações de humor.

Consultar o histórico dos ciclos.

Visualizar previsões estimadas de menstruação e ovulação.

Acompanhar padrões de humor e sintomas.

Criar uma conta e acessar seus dados em diferentes dispositivos.

Armazenar todas as informações pessoais na nuvem.

Editar, exportar e excluir seus próprios dados.

O aplicativo deve ter quatro telas principais na barra de navegação inferior:

Home.

Calendário.

Humor.

Ajustes.

A experiência deve ser pensada inicialmente para smartphones, com suporte a iOS e Android.

O nome do aplicativo será sempre escrito como Bloom, com B maiúsculo.

Não utilize nomes alternativos para o produto.

11. LÓGICA DO CICLO MENSTRUAL

Implemente uma camada de domínio independente da interface.

Toda a lógica de cálculo deve ficar em funções reutilizáveis e testáveis.

Não coloque cálculos de ciclo diretamente dentro dos componentes visuais.

11.1. Conceitos

Considere:

Primeiro dia da menstruação.

Duração do sangramento.

Duração do ciclo.

Ciclos anteriores.

Variabilidade do ciclo.

Data atual.

Registros corrigidos pelo usuário.

A duração do ciclo deve ser calculada a partir do primeiro dia de uma menstruação até o primeiro dia da próxima.

Não confunda duração do sangramento com duração do ciclo.

11.2. Previsões

Desenvolva uma lógica de previsão simples e transparente.

Quando houver histórico suficiente, utilize informações dos ciclos anteriores para estimar a próxima menstruação.

Quando houver poucos dados, utilize uma estimativa inicial claramente identificada.

Quando os dados forem insuficientes, não apresente uma previsão com falsa precisão.

As previsões devem ser atualizadas quando o usuário registrar uma nova menstruação.

Não modifique registros históricos para fazer as previsões parecerem corretas.

11.3. Fases do ciclo

Implemente uma representação estimada das seguintes fases:

Menstrual.

Folicular.

Ovulatória.

Lútea.

Deixe explícito que as fases são estimativas baseadas nos dados disponíveis.

Não afirme que a ovulação ocorreu em determinada data sem confirmação adequada.

Não utilize o aplicativo como método contraceptivo.

Não apresente uma previsão de ovulação como garantia de fertilidade ou infertilidade.

Inclua uma explicação acessível sobre as limitações das previsões.

11.4. Ciclos irregulares

O aplicativo deve aceitar ciclos com durações diferentes.

Não force todos os ciclos a terem 28 dias.

Não descarte automaticamente registros que estejam fora de um intervalo considerado habitual.

Quando os dados forem inconsistentes, solicite confirmação ou apresente uma mensagem informativa.

Não produza alertas médicos automáticos com base apenas na duração do ciclo.

12. MODELO DE DADOS

Projete um banco de dados relacional no PostgreSQL.

Crie migrações SQL completas.

12.1. Tabela profiles

Campos iniciais:

create table public.profiles (
  id uuid primary key references auth.users(id)
    on delete cascade,
  display_name text,
  locale text not null default 'pt-BR',
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);


Adicione as restrições e os índices necessários.

12.2. Tabela cycles

Armazene os ciclos menstruais.

Campos sugeridos:

create table public.cycles (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id)
    on delete cascade,
  start_date date not null,
  end_date date,
  notes text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);


Implemente validação para datas inconsistentes.

Não permita que um usuário consulte ou modifique ciclos de outro usuário.

12.3. Tabela daily_logs

Armazene os registros diários.

Campos sugeridos:

create table public.daily_logs (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id)
    on delete cascade,
  log_date date not null,
  flow_intensity text,
  symptoms text[] not null default '{}',
  notes text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique (user_id, log_date)
);


Valide os valores permitidos para intensidade do fluxo.

Considere utilizar tabelas relacionais para sintomas caso isso melhore a integridade e a evolução do projeto.

  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id)
    on delete cascade,
  log_date date not null,
  moods text[] not null default '{}',
  intensity integer,
  notes text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique (user_id, log_date)
);
